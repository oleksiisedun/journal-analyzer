# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Google Apps Script (clasp-managed) project bound to a Google Sheet. It automates reading daily `.docx` personnel-status reports out of a Google Drive folder and writing an attendance summary back into the sheet. There is no local runtime — all code executes in the Apps Script sandbox against the Sheets, Drive, and Docs services.

## Commands

- `clasp push` — deploy local `.js`/`.json` files to the live Apps Script project (script ID in `.clasp.json`).
- `clasp pull` — pull the live project's state back down (useful if the Apps Script editor may have diverged from these files).
- `clasp open` — open the Apps Script editor in the browser (useful to verify Advanced Service method/field names via autocomplete, or to read execution logs).
- There is no build step, linter, or test suite in this project — Apps Script runs the `.js` files directly, and correctness is verified by running `runAnalyzer` against a real Sheet/Drive folder.

## Sheet contract

The bound spreadsheet must have a sheet named `Main` (`MAIN_SHEET_NAME` in `Config.js`). Each row is one analysis job:

- `B` (`FOLDER_LINK_COLUMN`) — a Drive folder link or bare folder ID
- `C` (`POSITION_CHOICE_COLUMN`) — `"170"` or `"70"`, picked from a dropdown the operator configures manually in the Sheets UI (the script only reads/validates the value; it does not create or manage the data validation), selecting which `Handbook` position-name list applies to this row
- `D` (`REPORT_COLUMN`) — output; empty until processed

The bound spreadsheet must also have a sheet named `Handbook` (`HANDBOOK_SHEET_NAME`) with two lists of position names: column `A` for list `"170"`, column `B` for list `"70"` (`POSITION_LIST_COLUMNS` in `Config.js` maps each key to its Handbook column range). Every row is scanned using a regex built once per run (in `runAnalyzer`, via `SheetUtils.readPositionNames_` + `ReportBuilder.buildPositionHeaderRegex_`) from the position names in whichever Handbook list column C selects — there is no longer a single hardcoded position-header regex.

Running the "Journal Analyzer → Run analysis" menu item processes exactly **one** row per invocation: the first row (top to bottom) with non-empty B, a valid (non-empty, recognized) C, and empty D. Multiple rows require multiple menu invocations.

## Architecture

Apps Script concatenates every `.js` file in the project into one global scope — file boundaries here are purely organizational, not module boundaries. `Menu.js` (`onOpen`) installs the custom menu, which calls `Code.js`'s `runAnalyzer`. It asks `SheetUtils.js` (`findTargetRow_`) for the next eligible row, then opens the `Progress.html` modal dialog and hands off the rest of the work to it — the dialog's client-side JS repeatedly calls `Code.js`'s `processChunk` via `google.script.run`, each call processing as many files as fit in a `CHUNK_TIME_BUDGET_MS` (`Config.js`, 4 minutes) budget before returning progress plus a resumable state object for the next call. For each `.docx` file, `processChunk` calls `DriveUtils.js` (`convertDocxToGoogleDoc_` / `trashFile_`) and `DocxParser.js` (`extractDateFromFilename_`, `extractLines_`) to produce a flat array of text lines, which `ReportBuilder.js` (`scanLinesForPersonnel_`) scans into personnel entries; once the whole folder is processed, `ReportBuilder.js` (`buildReportText_`) builds the final report text written back to the sheet. See `README.md` for a diagram of this flow.

Key points a future change is likely to touch:

- **Folder processing is chunked to stay under Apps Script's 6-minute execution limit** (`Code.js:processChunk`), not because the codebase needs it for small folders, but because the ~30-file folders this tool normally processes can take several minutes end-to-end (~3 Drive/Docs API round trips per file: copy, open, trash). `runAnalyzer` only selects the target row and opens `Progress.html`; the dialog's client JS drives a `processChunk` call loop, passing back a plain, JSON-serializable `state` object (`fileInfos`, `fileIndex`, `personOrder`, `personDates`, `skippedFiles`) each round trip. `processChunk` checks the time budget **before starting each new file**, never mid-file, so a chunk boundary never interrupts `processFile_`. If the dialog is closed mid-run, nothing is left dangling — the report cell is only written on the final chunk, and each file's temporary Doc is already trashed in `processFile_`'s own `finally`. Skipped-file names are shown inline in the dialog on completion rather than via `SpreadsheetApp.getUi().alert()`, which doesn't work reliably while a modal dialog is already open.
- **Locking now covers only row-selection and each individual chunk, not a whole run**: `runAnalyzer` holds `LockService.getScriptLock()` just long enough to call `findTargetRow_`; `processChunk` acquires its own short lock per call (returning `{retry: true}` to the client on failure to acquire, rather than failing the run). This is a narrower guarantee than before — two dialogs opened close together could both pass `findTargetRow_` before either writes to the report column and end up processing the same row. Accepted as a limitation for this single-operator tool rather than adding a "claimed" sentinel or other persisted bookkeeping.

- **`.docx` can't be read directly** — Apps Script has no native `.docx` parser. `DriveUtils.convertDocxToGoogleDoc_` uses the Drive Advanced Service (`Drive.Files.copy` with `mimeType: MimeType.GOOGLE_DOCS`, enabled in `appsscript.json`) to make a throwaway Google Doc, which is opened with `DocumentApp` for text extraction and always trashed in a `finally` (`Code.js:processFile_`). If the copy call ever throws on the `name` field, the Advanced Service may be bound to v2 instead of v3, where the field is `title`.
- **Line extraction is a generic recursive walk** (`DocxParser.js:walkElement_`) over the whole document body — it doesn't special-case tables; `PARAGRAPH`/`LIST_ITEM` elements are the only leaf nodes that produce lines, everything else (including tables, rows, cells) is just recursed into.
- **The personnel state machine** (`ReportBuilder.js:scanLinesForPersonnel_`) is the core parsing logic and the most likely place for edge-case bugs. It walks lines with a single `inMatchingBlock` flag. Before any other check, a line matching any of `IGNORE_LINE_REGEXES` (`Config.js` — noise lines that should be skipped outright, e.g. stray artifacts) is dropped entirely: it neither starts/ends a block nor is recorded, as if the line weren't there. Otherwise, a block starts when a line matches the run's Handbook-derived `headerRegex` (passed in as a parameter — see the Handbook bullet below for how it's built), and ends on any of: a blank line, a line shaped like a position header (`GENERIC_POSITION_HEADER_REGEX`) that did *not* match `headerRegex` (i.e. some other position mixed into the same file), a line matching any of `BLOCK_END_REGEXES` (`Config.js` — other known non-personnel markers, e.g. `ппд`, `бпла`), or a line matching none of `RANK_REGEXES` (`Config.js` — recognized military rank prefixes, e.g. `солд`, `серж`; a genuine personnel line always starts with a rank, so a line without one ends the block instead of being recorded — append new ranks there as they're discovered in real documents). Rank is the sole signal for "is this a person" — there is no separate word-count heuristic. Only lines encountered while inside a matching block are recorded as personnel.
- **The per-row header regex is resolved once per run, from the `Handbook` sheet, not once globally**: `runAnalyzer` calls `SheetUtils.readPositionNames_(target.positionListKey)` to read the chosen Handbook column's names, trimmed, with blanks dropped and duplicates removed (first occurrence wins, via `[...new Set(names)]`), then `ReportBuilder.buildPositionHeaderRegex_` escapes each name (`ReportBuilder.escapeRegExp_`) and splices them into `POSITION_HEADER_TEMPLATE` (`Config.js`, e.g. `'^.+[«"“]POSITION_NAME[»"”].{0,10}$'`) as a single alternation, replacing the `POSITION_NAME` token with `(?:name1|name2|...)`. Because `state` travels through `google.script.run` round-trips as JSON, the compiled `RegExp` can't be stored directly — only its `.source` (`state.positionRegexSource`, a plain string) survives, and `processChunk` rebuilds `new RegExp(state.positionRegexSource)` once per chunk call (not per file) before its file-processing loop.
- **Person identity is the trimmed line text with leading markers and trailing `;`/`.` stripped** (rank + name together, e.g. `с-нт ГЛАДКИЙ А.В`) — `ReportBuilder.js:scanLinesForPersonnel_` strips a leading `LEADING_LIST_NUMBER_REGEX` marker (`Config.js`, e.g. `1)`/`2.`) and a leading `LEADING_ROLE_LABEL_REGEX` marker (`Config.js`, built from the `LEADING_ROLE_LABELS` array, e.g. `Пілот:`/`Штурман:` — append new labels there) from every line up front, and `trimTrailingPunctuation_` strips a trailing run of `;` plus a trailing run of `.` (source docs inconsistently end name lines with a stray `;` or an extra `.`) — except the trailing `.` is kept when it terminates a single-letter initial (`TRAILING_INITIAL_REGEX`, `Config.js`), so `Іванов О.В.` is preserved rather than becoming `Іванов О.В`. Otherwise the text is not normalized. The same person with a different rank prefix on a different date is treated as a different person by design.
- **Dates are tracked as a per-person set of ISO strings** (accumulated across chunks in `Code.js:processChunk`'s `state.personDates` — a plain object keyed by identity then by date, not a JS `Set`), de-duplicating repeated listings, then `ReportBuilder.collapseDatesToRanges_` renders them back to `DD.MM.YYYY`, merging consecutive calendar days into ranges. Row order in the final report is first-appearance order, which falls out of processing files sorted by their filename-derived date ascending (`Code.js:buildFileInfos_`).
- **Column positions are resolved at runtime, not hardcoded**: `Config.js` defines `FOLDER_LINK_COLUMN` / `POSITION_CHOICE_COLUMN` / `REPORT_COLUMN` as open-ended A1 ranges (e.g. `'D2:D'`), and `SheetUtils.columnNumber_` converts one to a numeric index via `sheet.getRange(a1).getColumn()`; `findTargetRow_` reads each row's cells by that resolved offset rather than assuming a fixed destructuring order, so the three columns don't need to stay adjacent-and-in-order. The `Handbook` sheet's per-list ranges (`POSITION_LIST_COLUMNS`) are resolved the same way.
- **Invalid or empty outcomes are written back to the report column**, never left blank, so a row is never silently reprocessed or silently skipped forever: `ERROR_INVALID_LINK` for rows that fail folder-link validation, `ERROR_INVALID_POSITION_LIST` for a non-empty but unrecognized column-C value, `NO_FILES_MARKER` / `NO_MATCH_MARKER` for folders that produce nothing. Files that fail to process (undated filename, conversion error) are collected into `skippedFiles` and shown inline in `Progress.html` once the run finishes. This differs for Handbook setup problems: an empty column C is treated as "not ready yet" and silently skipped (like an empty B), but a missing `Handbook` sheet or an empty resolved name list for an otherwise-valid C is treated as a configuration error and surfaces as an uncaught exception (Apps Script's default error alert) rather than being written to D.

## Required OAuth scope

Because the script must read arbitrary pre-existing Drive folders (not just files it created itself), it needs the broad `.../auth/drive` scope, not `drive.file`. `appsscript.json` intentionally leaves `oauthScopes` unset so Apps Script auto-detects the required scopes from code rather than needing manual upkeep.
